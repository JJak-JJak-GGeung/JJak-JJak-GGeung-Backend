# 짝짜꿍 공통 입출력 v1

**[팀 제안]** 아래 필드·경로는 본선에서 구현할 약속이다. **[확정]** 수량·금액·상태는 R01~R10에 따른다. ID는 서버가 발급하는 불투명 문자열이다. 예시의 P·T·S는 각각 정산·거래·승인본 ID를 줄여 쓴 것이다. 날짜는 YYYY-MM-DD, 수량·단가는 십진 문자열, 원화 금액은 원 단위 정수다. 모름은 null, 확인한 영은 "0" 또는 0이다. 빈 문자열·누락 키로 null을 대신하지 않는다.

**구현 경계 · 제안 경로**　박승원이 Frontend 저장소의 lib/의 Flutter Web·Riverpod·GoRouter와 Backend 저장소의 app/photo의 사진 판독을 맡는다. 이성찬은 Backend 저장소의 app/voice, 안홍모는 Backend 저장소의 app/reconcile을 맡는다. 구본혁은 Backend 저장소의 app/api·Backend 저장소의 app/workflow·Database 저장소의 supabase/migrations/·배포 설정에서 FastAPI·LangGraph·Supabase를 연결한다. Vercel 프런트는 HTTPS FastAPI 주소에 점주 세션의 접근 토큰을 보낸다. 서버가 토큰과 점포 소속을 검증한다. 홈의 GET /api/periods는 그 점주의 기간 목록을 반환하고, 기간을 고르면 GET /api/periods/P를 읽는다. OpenAI API 키와 서버용 Supabase 비밀키는 백엔드에 둔다.

**A 화면 예시** · 단위 kg. 주간 100/100/96(명세/유효 청구/확인 수령), 차이 +4, check_amount 80000, billed_amount 2000000. 개별 DL-A131은 40/40/36. MISMATCH, 확인 중, can_approve=false, approvable_amount=null, approved_amount=null, payment_status=UNCONFIRMED. 확인 메모는 진술 충돌(CONFLICTING)을 남긴다. 합의된 수정본은 주간 100/96/96, 현재 차이 0, billed_amount=approvable_amount=1920000, can_approve=true, approved_amount=null. 직접 승인하면 approved_amount=1920000, 동일 버전 추가 승인은 기존 ID, 송금 미확인.

**상태와 저장 원칙** · 단가나 환산 근거가 없어 금액을 계산할 수 없으면 check_amount=null. 음수 차이는 방향을 함께 표시한다. DOCUMENTS_ONLY는 실입고 미확인. 확인한 수령까지 있으면 RECEIPTS_INCLUDED. 문서 일치라도 수령이 없으면 전체 대조 MISSING_DATA, received_qty·delta_qty·check_amount=null. 화면 ‘확인 중’은 예시에서 work_status=WAITING_REPLY, ‘승인 가능’은 MATCHED와 빈 blockers 등 현재 근거에서 도출. 서버는 근거가 실제로 추가·확인·정정될 때 해당 기간의 input_revision을 올린다. 점포·거래처가 다른 자료는 분리한다. 실패한 판독은 기존 문서 ID로 재시도한다. 같은 요청 키에 다른 내용은 충돌이다. 최초 승인 시 버전·차단 사유 재검사와 스냅샷 저장을 한 트랜잭션으로 처리한다. 지난 버전의 새 요청은 409 STALE_REVISION와 최신 버전, 미해결 차이는 422 BLOCKED와 사유를 돌려준다. 점주가 최신 화면에서 다시 판단한다.

**행 식별과 판정** · 계산 결과의 evidence_refs 각 항목은 document_id, line_id(문서 머리글·하단은 null), source_location, 근거 종류를 가진다. 쪽·행 또는 문구로 원본에서 다시 찾을 수 있어야 한다. 확인 수령은 receipt_id, source_line_id, target_delivery_line_id, received_qty, unit, confirmed_by, confirmed_at을 갖는다. 확인한 점주 입력은 행 정정 이력으로 남긴다. 읽은 수량의 출처가 명세·수령 기록·유효 청구인지에 따라 declared_qty·received_qty·billed_qty를 따로 채운다. 현재 실수령 미확인은 work_status=NEEDS_INFO, 차이 확인 중은 WAITING_REPLY, 근거 충족 후 승인 전은 OPEN과 can_approve=true, 승인 뒤는 APPROVED와 고정된 approved_amount다. 거래 근거가 바뀌면 새 검토의 승인액은 null이 되고 과거 승인본은 ID로 계속 조회된다.

### 화면·서버 연결에 쓰는 세부 약속

- **파일 전송**　문서와 전사는 각각 multipart/form-data의 file 한 개를 받는다. 문서 요청에는 doc_type 힌트와 request_key를 함께 보낸다. 전사는 브라우저가 실제 녹음한 파일과 MIME을 받아 draft_text 한 필드만 응답한다. 두 요청 모두 점주 인증을 사용한다. 마이크 거절과 전사 실패는 편집란을 직접 입력할 수 있는 상태로 둔다.
- **재조회와 원본**　GET /api/transactions/T는 해당 거래의 근거와 확인 메모 목록(memos)을 반환한다. 메모에는 memo_id, transaction_id, confirmed_text, source_mode, 작성자와 확인 시각이 있다. 화면은 비공개 원본을 열 때 같은 브라우저 프로필에 저장된 임의 접근 키로 기존 original 경로에 요청해 받은 파일을 표시한다. 승인본에는 document_id와 당시 행 위치·값을 저장한다. 같은 기기·브라우저 프로필·배포 주소로 다시 열면 같은 ID의 원본을 조회한다. 사이트 데이터를 지우거나 다른 프로필로 열면 새 보관함을 사용한다.
- **일부 수령만 확인**　청구 대상 납품 중 한 행이라도 수령이 누락되거나 단위 비교가 불가능하면, 해당 행과 주간 전체의 delta_qty·check_amount 및 주간 approvable_amount는 null이다. 주간 전체 received_qty가 확정되지 않으면 null로 보낸다. 확인된 행의 수량·차이와 원문 단위는 그대로 표시한다. 청구와 수령이 모두 있는 행을 0kg 수령으로 확인한 경우에는 "0"을 유지한다. 수령 하나 이상을 포함하면 확인 범위는 RECEIPTS_INCLUDED이고, 전체 승인 가능 여부는 별도로 판단한다.
- **수령 확인 두 번**　첫 receipt_link 성공 응답의 input_revision을 두 번째 확인 요청의 expected_revision으로 보낸다. 문서 머리글의 합의 근거는 line_id가 null이어도 document_id와 원문 위치로 다시 열 수 있어야 한다.
- **정정·충돌 처리**　이미 성공한 요청의 재전송은 권한·본문 일치를 확인한 뒤 기존 ID를 반환한다. 구버전 새 요청의 409 STALE_REVISION은 최신 근거를 다시 보여준다. 같은 키에 다른 본문인 409 KEY_REUSE는 새 승인으로 자동 재시도하지 않는다. 최신 버전에서 근거가 부족한 422 BLOCKED에는 blockers를 담는다.

### 검수에서 직접 쓸 입력·저장 약속

- **시작 상태**　각 독립 세트에 점주가 접근할 빈 점포·거래처·기간을 준비한다. 홈에서 점포·기간을 확인하고 반환된 실제 ID를 사용한다. 수량이나 거래를 예시로 미리 채우지 않는다.
- **수령 입력과 정정**　POST /api/periods/P/confirmations에서 기존 수령 원본 연결은 kind=receipt_link, 점주가 직접 근거를 적는 수령은 kind=receipt_entry로 한다. 직접 입력은 target_id(납품 행), received_qty(십진 문자열), unit, evidence_text, expected_revision, request_key를 보낸다. 서버가 작성자·시각과 근거 ID를 붙인다. 이미 확인한 수령의 정정은 kind=line_correction에 target_id, supersedes_receipt_id, corrected_fields, 정정 근거·버전·키를 보낸다. 자료 버전과 새 수령 ID를 돌려주고 이전 이벤트는 이력에 남긴다. 같은 확인을 반복해도 수령·버전을 두 번 늘리지 않는다.
- **원본 필드 영속화**　최종 DBML을 기반으로 원문 거래처, 납품 번호·일자, 청구 대상 기간, 수정 청구의 원문 대체 번호, 합의 문구와 원본 위치를 저장한다. DBML에 직접 대응하는 열이 없는 값은 본선에서 원본별 판독 메타데이터로 보완한다. receipts.doc_line_id는 대상 납품 행으로 쓰고 수령 원본의 source_line_id 또는 점주 입력 근거 ID·단위를 별도 보존한다. 원본 단위와 기준 단위를 구분한다.
- **거래처·기간 경계**　업로드할 때 고른 거래처와 원문에 적힌 거래처가 다르면 원문을 별도 거래처 또는 미분류 기록으로 보관한다. 선택 중인 청구의 합계와 연결은 유지한다. 발행일 대신 청구서에 적힌 대상 기간과 납품일을 확인한다. 수정 대상으로 보이는 문서에 신뢰할 수 있는 번호·연결 근거가 없으면 후보로 보류한다.
- **화면 버전**　승인 클릭은 화면에 표시한 expected_revision으로 전송한다. 통신 재시도는 같은 키·본문을 쓰며 성공했던 요청은 같은 ID로 응답한다. 별도의 구버전 승인 요청에는 최신 근거를 반환하고 점주의 새 클릭을 기다린다. 금액 확정·버전 확인은 서버에서 원자적으로 처리한다.

이미 승인한 현재 자료 버전의 조회 응답은 work_status=APPROVED, can_approve=false, approved_amount=승인 당시 금액으로 표시한다. 응답 유실로 같은 성공 요청을 다시 보내면 승인본 ID를 재전달한다. 새 근거가 들어온 현재 화면의 승인액은 다시 null이며 과거 승인본 상세는 그대로다.

**DBML과 승인 계약**　자료가 바뀔 때 올라가는 input_revision과 발급한 승인본 순번 version_no는 다르다. DBML에는 기간+요청 키 및 기간+승인본 순번의 유일성이 있다. 같은 기간·자료 버전으로 서로 다른 키가 동시에 들어오는 경우까지 막도록 구본혁이 본선에서 기간 잠금 또는 기간+자료 버전 유일 제약을 적용한다. 승인 스냅샷·근거·금액을 한 트랜잭션에 저장하고 같은 성공 요청은 기존 ID로 응답한다. 같은 키에 다른 본문은 충돌이다.
